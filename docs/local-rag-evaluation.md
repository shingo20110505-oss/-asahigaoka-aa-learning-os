# 教材検索とローカルLLMの比較

2026-10-28。**通常チャットへの採用は保留。測定ページのみ公開する。** Gemma 4でも未知問題で南北半球の誤断定が残った。iPad A16の実機結果はまだない。

## 方法

- 開発24問（地理8・歴史4・古文4・漢文3・英語4・資料不足1）。質問と採点基準は experiments/rag/questions.mjs。採点基準はモデル・検索へ渡さない。
- 検索なし、検索原文、検索＋LLMを同じモデル・同じ質問で比較。教材定義と専用計算を優先する実用方式は別枠。この成績をLLMの正答率とは呼ばない。
- v7の未使用12問（holdout）はteachの語形誤断定を検出。v8では別の12問（validation）を実施前に固定。後者でも半球の誤断定が出た。同じ問題への修正を未知問題の改善として数えない。
- v8は上位2件・合計600文字。否定の直前などで文章を切らない。質問と句点などで分けた最大4クエリを使用。通常Codexの検索回数を制限する仕組みではない。
- context 2048、並列1、batch 512、seed 42、最大512 tokens。モデル別sampling設定はmodels.json。質問ごとのKV再利用なし、生成順は問題ごとに反転。実際のプロンプトと教材・検索・実行コードのハッシュを保存。
- 推論前にウォームアップ。取得・ロード・索引作成は回答時間と別。初回文字はWorkerで空白以外を得た時点で、画面描画の完了ではない。RAGと実用方式には検索時間を加算する。

全モデルはUnsloth変換。リビジョンとSHA-256固定。候補登録は採用ではない。GemmaのE2Bは有効規模の名称で、必要RAMが2GBという意味ではない。容量と実行RAMは別。

wllama 3.8.1と同版Safari互換版を自己ホストし、npm integrity確認後に取得。Windows Chrome / AMD RDNA2はPC参考値。GPUログのバッファ値は総ピークRAMではなく、A16の余裕を推定する根拠にはしない。

Qwen3.5は同一GGUFをOllama/CPUでも確認し、追加説明に誤りが残った。ブラウザだけの問題とは判断できない。ブラウザのInvalid magic numberは推論中の通信デコードで発生。ファイル破損やOOMとは断定しない。

## 採点結果

必要な答えと理由が揃い、追加説明にも誤りがなければ完全正答。不足は部分正答、誤り・回答不能は0点。安全な回答保留も正答率には加えない。原文から別の数値を計算する必要がある場合も完全正答にしない。キーワード一致率は使わない。

Gemma v5・開発24問（PC）：

| 方式 | 完全正答 | 初回文字 中央値 | 完了 中央値 / 95%点 |
| --- | ---: | ---: | ---: |
| 検索なし | 9/24 | 2.298秒 | 4.337秒 / 6.321秒 |
| 検索原文 | 20/24 | 0.008秒 | 0.008秒 / 0.025秒 |
| 検索＋LLM | 17/24 | 6.750秒 | 7.841秒 / 16.678秒 |
| 教材定義を優先 | 20/24 | 4.112秒 | 5.955秒 / 16.678秒 |

Gemma v8・新しい未使用12問（PC）：

| 方式 | 完全正答 | 初回文字 中央値 | 完了 中央値 / 95%点 |
| --- | ---: | ---: | ---: |
| 検索なし | 6/12 | 2.243秒 | 3.861秒 / 6.097秒 |
| 検索原文 | 10/12 | 0.008秒 | 0.008秒 / 0.029秒 |
| 検索＋LLM | 11/12 | 4.813秒 | 6.339秒 / 13.481秒 |
| 教材・計算を優先 | 10/12 | 4.813秒 | 6.340秒 / 13.482秒 |

v8実用方式は1件の誤断定（7月が最も暑い都市を南半球と回答）と1件の回答保留（未分類の語形）。初回文字95%点も10.858秒で目安を超える。正答数だけで採用しない。v1/v5/v8は文脈長・問題セット等が異なるので、モデルだけの純粋な性能差として比較しない。

保存済みGemmaのPCロードは約12〜14秒、初回取得＋ロードは約159秒。ChromeをオフラインにしHTTPサーバーを停止した全ページ再読み込みで、未キャッシュ通信の失敗と3問の実行完了を確認。A16の結果ではない。

採点定義はexperiments/rag/grade-*.mjs。生回答と採点はdocs/evidence/local-rag/、追加診断はローカルtest-results/rag/に保持。

v8の開発24問を再実行した実用方式は21/24完全正答、2件説明不足、1件回答保留。14/24件はLLMを使わず教材・計算・不足判定を返したため、完了中央値0.026秒、95%点13.913秒。LLMだけの生成速度ではない。純粋な検索＋LLMは17/24、完了中央値7.753秒。未知12問の誤断定があるため、これも採用根拠にはしない。

**本体チャットにはまだ接続していない。** 現在はオフラインで保存済み履歴を読む動作。実機・品質の合格後、既存ChatArchiveの役割・ID・期限検査、Worker停止、実行資産のオフライン保存を含めて統合する。測定ページのService Workerだけでは通常チャットのオフライン推論にならない。

## iPad互換処理のABORT対策（表示版 2026-10-28.10）

ユーザーからiPadで「abort」の報告を受け、Windows ChromeでSafari用互換処理を強制して再現した。PCでの互換確認であり、物理iPad A16の測定ではない。

| 構成 | 互換処理での確認結果 |
| --- | --- |
| 3.8.1、3.11GBの単一GGUF | mmap failed: Out of memory。ロード成功扱いの後、準備運転でABORT |
| 3.6.1、単一GGUF | unexpectedly reached end of file、準備運転でABORT |
| 3.8.1、公式ツールによるGGUF分割 | ロード後の準備運転でmemory access out of bounds |
| 3.6.1、GGUF分割 | 読み込み・回答まで完走 |

Safari互換処理のみ、SRIを固定したwllama/compat 3.6.1の組み合わせを使用する。通常のChromiumは3.8.1のまま。モデルの量子化・重み・システム指示は変更していない。各結果に実行版と互換処理・強制検証の有無を記録する。

2GiB以上の単一GGUFは、保存済みBlobを有効なGGUFパートに組み直す。テンソルを再量子化せず、元データをBlob.sliceで参照する。モデル全体をArrayBufferに展開せず、別コピーを永続保存せず、再ダウンロードもしない。Gemmaは5パート、最大1,630,591,264 bytes。大きな一つのテンソルを分割できないため、全パート512MB以下という意味ではない。

独立したllama-gguf-split b11960で再結合し、gguf 0.19.0のReaderで全601テンソルの名前・型・形状・SHA-256一致を確認した。使用した公式WindowsツールZIPのSHA-256は73f962f82850d244db47eaacb9d913637027b82399124324298576d58c5f4287。

修正版のPC互換3問では、ロード24.821秒、検索＋LLMの完了中央値8.409秒、初回文字中央値5.600秒。これをA16の性能や合格根拠とは扱わない。問題の正答数を増やす修正ではなく、検索なしの誤答・検索付きの説明不足は残る。

通信を切りHTTPサーバーも停止して完全再読み込みした再試験では3問完走。ロード29.005秒、検索＋LLM完了中央値9.110秒。未キャッシュfetchの失敗と外部ネットワーク要求0件を確認した。試験用HTTPサーバーの終了待ちを避けるため接続も明示的に閉じた。ローカルblob Workerの生成は外部通信に数えない。

ダウンロード・保存済みファイル・GGUFパート作成・GPU読込を分けて表示し、直前の段階と進捗をJSONへ記録する。接続確認はRange 0–31のGETでGGUFヘッダーを検査し、応答本文を取り消す。HTMLの制限ページ、HTTP失敗、無応答を区別する。保存容量の不足は読込前に止め、GPU対応と保存済みモデルの有無を表示する。これは物理RAM容量の検査ではない。

ロード中に進捗が60秒止まった場合、GPU読込が180秒終わらない場合は記録を残して停止する。単なるABORTをメモリ不足とは断定せず、ログに該当する証拠がある場合だけその説明を表示する。モデルのメタデータが得られないロードは成功扱いにしない。

生の回帰診断と修正版結果は `docs/evidence/local-rag/compat-loader-20261028.json`。推論プロトコルはv8だが、実行版・教材ハッシュが違う結果の精度や時間を同一条件として扱わない。

参考：[wllama公式の互換処理](https://github.com/ngxson/wllama/blob/master/compat/README.md)、[GGUF分割の公式説明](https://github.com/ggml-org/llama.cpp/blob/master/tools/gguf-split/README.md)。

## 2026-10-29: iPadの実測記録に基づく読み込み時の割り当て削減

ユーザー提供の測定JSONを印刷したPDFを確認した。画面v10、Safari互換3.6.1が適用済みで、3回とも`runtime`段階で中断、回答数は0。初回の3,106,738,272 bytesのダウンロードは完了し、その後の2回は保存済みデータを使用している。ユーザーはページが自動で再読み込みされた／消えたと報告した。タブやブラウザの終了が疑われるが、OSの終了理由は記録されていない。`interrupted`の日時は次回ページ起動時であり、正確なクラッシュ時刻ではない。保存容量やWebGPUのバッファ上限を物理RAM容量とは扱わない。

固定された3.6.1の非同期ファイル読み込みは、大きな`fread`を一つのArrayBufferにしてからWASMへコピーする。Gemmaの`per_layer_token_embd.weight`は1,614,807,040 bytes。Windowsで同じ互換処理を計測し、実際にそのサイズの転送要求を確認した。

SRI検証後のSafari向けJSラッパーに、8MiBずつ順番に読み込み、WASMの所定位置へ書く変更を適用する。独立した新モデルや再量子化ではなく、元のモデルの同じバイト列を使用する。短い読み込み、EOF、エラー、WASMメモリの再割り当てを検証し、上流のコード構造が変わった場合はビルドを失敗させる。通常のChromium用ライブラリは変更しない。

互換処理の計算バッチは128、内部バッチは32。文脈2048、GPUレイヤー99、モデル、質問、回答採点基準は維持し、実際に使った設定は`conditions.effectiveLoadOptions`と`loadChecks.loadOptions`に保存する。条件が違う測定を同一設定の速度・精度として集計しない。

| Windows上の強制互換試験で測った項目 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 1回のファイル転送の最大バイト数 | 1,614,807,040 | 8,388,608 |
| 読み込み要求の合計バイト数 | 3,712,966,656 | 3,712,966,656 |
| GPU計算バッファ（ネイティブログ） | 114.51 MiB | 7.14 MiB |
| CPU計算バッファ（ネイティブログ） | 26.52 MiB | 1.64 MiB |

これはブラウザ全体の最大使用メモリを測った値ではない。モデル常駐領域はCPU 1782.25MiB、GPU 1381.49MiBのまま。変更後の3問は完走し、ロード29.615秒、検索＋LLM完了中央値9.710秒。変更前は英語1問の診断だったため、回答中央値の前後比較による高速化は主張しない。回答品質の改善・iPad A16での成功もまだ主張しない。

ネイティブログを読み込み中から約0.5秒間隔で端末へ保存する。ページが閉じる際の通知も別に記録し、再起動した画面は「前回中断」と表示する。ログのない中断をメモリ不足と断定しない。

配信用の無計測コードでも通信遮断＋HTTPサーバー停止＋完全再読み込み後に3問完走した。未保存URLへの通信失敗、外部通信0件、ロード26.989秒、検索＋LLM完了中央値9.813秒を記録した。

根拠は`docs/evidence/local-rag/ipad-load-memory-20261029.json`。公開後、保存済みモデルを使うiPad実機の再測定が必要。

参考：[wllamaの非同期ファイル読み込み](https://github.com/ngxson/wllama/blob/master/README-dev.md#async-file-read)。

## 2026-10-30: v11実機中断の追跡と省メモリ候補（画面v12）

ユーザー提供のJSONでは画面v11、8MiB読み込み、バッチ128・内部バッチ32が適用済みだった。ダウンロードは完了しているが、モデル配置中に中断し、完了した問題は0。したがって前回の対策でiPadの問題が解決したとは扱わない。OSによる終了理由は取得できていない。

WindowsでGPUのバッファ上限を実機の記録と同じ1GiBにしても、Q4モデルの読み込みと英語1問は完走した。この上限だけでは中断を再現しない。ネイティブログの「1024 MiB free」は総RAMや実測した空きVRAMではない。

GGUF分割時、辞書などのメタデータを全パートに重複して入れていた。公式ツールに合わせ最初のパートだけに保持し、既定値以外のアラインメントのみ後続パートにも残す。重複する63,136,128 bytesを除去し、公式ツールで再結合後に全601テンソルの型・形状・SHA-256一致を独立確認した。ただし、計測したWASMヒープ容量は変更前後とも2,274,754,560 bytesであり、この修正だけによるメモリ不足解消は主張しない。

同じGemmaのQ3_K_Mを測定候補へ追加し、測定画面の初期選択にした。通常チャットのモデルは変更していない。これはQ4とは異なる量子化データで、新たに約2.54GBの取得が必要。ダウンロードした実ファイルのSHA-256は固定した配信元の値と一致した。

| Windows強制互換処理・GPUバッファ上限1GiBでの計測 | Q4_K_M | Q3_K_M |
| --- | ---: | ---: |
| ファイル容量（bytes） | 3,106,738,272 | 2,536,786,016 |
| load完了時のWASMヒープ容量（bytes） | 2,274,754,560 | 1,874,198,528 |
| CPUモデルバッファ（MiB） | 1782.25 | 1451.25 |
| GPUモデルバッファ（MiB） | 1381.49 | 1117.94 |

ヒープ容量は約17.6%減ったが、ブラウザ全体のピークRAMや実機での安定性を測った値ではない。GPU上限を合わせた検証もiPadのエミュレーションではない。

Q3の3問は完走し、検索＋LLMの完了中央値10.660秒、95%点16.107秒。ただし古文の「うつくし」を現代語の「美しい」と同じと誤断定した。品質不合格で、通常チャットへは採用しない。短い試験の成績を全科目の正答率に一般化しない。初回ロード195.073秒はダウンロード込みであり、保存済みロードとの速度比較には使わない。

詳細な実測・生回答・オフライン試験は `docs/evidence/local-rag/ipad-v11-followup-20261030.json`。GPU上限とヒープ計測用の一時コードは配信に含めない。画面には表示版と測定方式の両方を明記し、測定方式v8を古い画面と取り違えないようにした。

## 実機確認

iPad A16の実機で/labs/rag/update.htmlを開き、画面2026-10-30.12を確認する。iPad A16と省メモリ候補Q3_K_Mを選び「短い動作確認（3問）」を開始。初回約2.54GB。以前のQ4とは別のモデルなので、Q4の保存だけではオフラインで開始できない。モデルは開始ボタンを押すまで取得しない。JSONは端末に保存し、外部へ自動送信しない。個人ファイル・ログイン情報・会話履歴は参照しない。
