# 手書き消去の比較と採用判断

評価日：2026-10-26。実機：Windows 11、AMD Ryzen 5 7535U、CPU 6スレッド。A16 iPadの実測ではない。

## 採用する構成

RISEに組み込むのは、端末内での赤・青の候補抽出、手動の「消す／残す」ブラシ、周囲の紙色による限定補修、原本・結果の比較と別保存。色検出だけでは黒い手書きを判定できない。赤・青の印刷も候補になるため、結果を確認して「残す」で調整できる。

難しいページには明示的な「AIで仕上げる（PC）」を用意する。原本を資料室に保存して既存のAI消去へ渡す。これは生成AIの別経路であり、今回の専用モデルを動かす機能ではない。通常の色消去やプレビューでPCへ画像を送らない。

専用モデルを採用しなかった理由は、速度だけでなく印刷保持と消し残しを評価した結果による。**「AI専用モデルより色処理があらゆる教材で優れている」という結論ではない。黒い筆記の完全自動消去と全ページ5〜10秒を達成したとは扱わない。**

## 比較対象と準備状況

|方式|実施内容|判断|
|---|---|---|
|RISEの色抽出＋紙色補修|同じ日本語合成画像で実行、マスク外の画素不変を検証|軽い通常処理として採用。黒は手動指定、色印刷は保護指定が必要|
|OpenCV Telea inpaint|CPUで色マスクと組み合わせ、同じ画像の1・3・10枚を実行|処理可能。ただし色選択の誤りは解決しない。ブラウザへ追加ライブラリを配布する利点が今回の紙色補修では小さいため通常経路に不採用|
|DIS-Handwriting-Remover|配布重みを取得し、安全なstate_dict読み込みで512/1024入力を実行。さらに著者方式の縦横比保持＋パディング、および公開検証画像5枚も実行|消し残しと印刷欠損があるため自動消去の既定値に不採用|
|HandWritingEraser-Pytorch / DeepLabv3+|ソース、タイル推論、コードMITを確認。著者の重みリンクはBaiduの共有初期画面に到達するが、直接取得・検証できる重みを確保できなかった|未実行。劣っていると判断したわけではない。無関係な重みで代用しない|
|LaMa|公式コード・入力仕様・配布リンクを確認。マスクが必要な補完器で、手書き検出器ではない。コードApache-2.0とは別に、配布重みの条件を公式資料から確定できず|重みは配布・実行していない。隠れた問題文の正確な復元を保証できるものではなく、今回の既定経路に不採用|

一次資料：[DISモデル](https://huggingface.co/Inoob/DIS-Handwriting-Remover)、[DISソース](https://github.com/xuebinqin/DIS)、[著者の推論コード](https://github.com/ivanhe123/Handwriting-Removal-DIS/blob/main/Inference.py)、[DeepLabv3+実装](https://github.com/AndSonder/HandWritingEraser-Pytorch)、[LaMa公式](https://github.com/advimman/lama)、[LaMaの重み条件に関する未解決の確認](https://github.com/advimman/lama/issues/368)。

## 合成画像の品質検証

1200×1600の5条件（赤青、黒、黒と印刷の重なり、赤い印刷、影）。日本語の問題文・数式・罫線・三角形を印刷として描き、別レイヤーの折れ線と楕円を筆跡として重ねた。手書きフォントを印刷と呼び分けただけの画像ではないが、実際の写真・人の筆跡の代替ではない。

全方式の比較は同一画像を使用した。保持率は筆跡で隠れていない印刷画素のうち、消去マスクに入らなかった割合。隠れた印刷の復元を意味しない。生の測定結果は [handwriting-evaluation-results.json](handwriting-evaluation-results.json)。

|条件|RISE色検出 筆跡再現率|RISE色検出 印刷保持率|DIS 1024・縦横比保持 筆跡再現率|同 印刷保持率|
|---|---:|---:|---:|---:|
|赤・青の筆記|100%|100%|100%|99.39%|
|黒の筆記|0%|100%|2.25%|99.98%|
|黒と印刷の重なり|0%|100%|23.46%|100%|
|赤い印刷を含む|100%|96.02%|100%|94.74%|
|影のある紙|100%|100%|100%|99.31%|

RISEの色候補には、同色の印刷を誤って消す明確な弱点がある。このため「候補表示→残す範囲の指定→結果確認→コピー保存」とした。保護ブラシで指定した印刷画素が原本と一致すること、消去マスク外はRGBAすべてが一致することを自動テストした。DISの結果も目視し、赤い問題文の欠落と罫線の穴を確認した。

DISは512入力では黒の筆跡再現率0.16%、1024へ全体を変形して入力した場合も5.53%。縦横比保持の結果だけを恣意的に選んで採否を決めたものではない。

## 実際の公開検証画像

[公開データセット](https://huggingface.co/datasets/Inoob/HandwritingSegmentationDataset)の `val.zip` からファイル名順の最初の5枚を選び、DIS 1024・著者方式のパディングで実行した。中国語資料の領域であり、日本語教材の実測ではない。またモデル選択から完全に独立した評価データかどうかは確認できない。画像はRISEへ再配布しない。

5枚の単純平均は、精度96.05%、筆跡再現率82.23%、IoU79.22%。筆跡以外の暗い画素の保持率は98.97%だった。個別の筆跡再現率は64.99〜90.47%。本来の領域では機能するが、確認なしで問題文を消してよい精度ではない。合成画像の結果だけから「モデル自体が無効」と結論しない。

## 処理時間とメモリ

CPUを使用。モデルは最初に一度読み込み、画像は逐次処理した。DISの速度はPNG読み込み・推論・PNG書き出しを含む。Web転送、ブラウザ表示、iPadの性能を含まない。1回の比較測定であり、安定したp95を保証しない。

|方式|1枚|3枚|10枚|
|---|---:|---:|---:|
|DIS 512|0.57秒|1.59秒|5.47秒|
|DIS 1024（縦横比保持）|1.70秒|5.00秒|16.43秒|
|OpenCV色マスク＋Telea|0.13秒|0.34秒|1.17秒|

DIS 1024の重み読み込みは0.33秒、プロセスの最大ワーキングセットは約1621MiB。モデルの176.7MBというファイル容量と実行時メモリは異なる。

RISEのJavaScript画素処理のみでは1・3・10枚が約0.02・0.10・0.19秒だったが、これは画像の読み込み・書き出しを含まないため、上表との直接比較や「送信から結果まで」の値には使わない。実際のブラウザには1・3・10枚の自己計測を用意し、生成・PNG化・デコード・Worker処理・結果PNG化を含む時間と端末情報を表示する。通常の1枚処理にも読み込みから結果生成までの実測値を表示する。

## 実装上の保証と範囲

- 入力ファイルを更新しない。原本と結果を資料室へ別ファイルで保存する。途中のプレビューは保存済み資料を上書きしない。
- ローカル消去では選択マスク外の画素を変更しない。生成AIの別経路にはこの保証を拡張しない。
- 枚数制限は設けず、展開する画像は1枚ずつにする。1画像1600万画素まで。過大画像は明示的にエラーにし、黙って縮小・劣化させない。
- Web Workerで処理。対応しないブラウザは逐次のCanvas経路に切り替える。中止は処理中Workerと未開始の処理を破棄する。
- インストール済みのRISEキャッシュがあればローカル処理はオフラインでも使える。学習済みモデルのダウンロードや有料APIは通常処理に不要。
- A16実機で検証済みとは記録しない。PCの推論速度や画面サイズのエミュレーションで代用しない。

## 再現手順

`node --test tests/rise-handwriting-clean.test.mjs` と `node scripts/handwriting-engine-benchmark.mjs` は追加依存なしで実行できる。

専用モデルの評価はアプリと別のPython仮想環境を使う。評価時の依存はPython 3.12、torch 2.14.1+cpu、numpy 2.5.4、Pillow 13.0.0、opencv-python-headless 5.0.0.93。`scripts/handwriting-model-eval.py`、`scripts/handwriting-same-fixture-benchmark.mjs`、`scripts/handwriting-opencv-eval.py` が再現スクリプト。モデル・データ・仮想環境はGitへ追加しない。

DISソースはコミット `b6764e20381f6f42a70f83fa3324181529ed1403` の `IS-Net/models/isnet.py` を読んで確認した。未使用のtorchvision importだけを除いて利用し、元ファイルSHA-256を実行前に固定値で照合する。重みもSHA-256照合し、`torch.load(..., map_location='cpu', weights_only=True)` と厳密なstate_dict読み込みを使った。公開推論スクリプトをそのまま実行していない。

- 重み：`d685cc76a8c4d6aebf9a82499b7771d13aaa27ebd90e933036bdd004db4beefa`
- モデル定義：`83505426387792a3cb9357254a5e21547cd074710d120485960aa8cc9d0b39bb`
- 公開検証ZIP：`452ce1edcb8b633a19fc5a48c50877efa6808d7941918f8f4118f4fbae4016c1`

公開モデルの推論サンプルは不足する名前やCPU時にCUDAを指定する箇所があるため、RISEの比較ハーネスではCPU入力を明示した。BGR入力、0.5減算、出力正規化、0.35のマスク閾値を合わせ、全体リサイズと著者型パディングの両方を比較した。元画像の全体二値化は採用せず、選択マスクだけを元画像に合成した。
