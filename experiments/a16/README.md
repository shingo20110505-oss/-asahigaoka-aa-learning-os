# RISE A16 比較ラボ

本番とは独立したブラウザ内LLMの実験。アプリのインストール、有料API、ログイン、PC推論サーバーは不要です。初回取得後のオフライン動作を検証します。**PCの結果はiPad A16の性能を証明しません。**

## 起動

開発用PCにNode 24とtarがある場合、リポジトリのルートで実行します。

```powershell
node experiments/a16/setup-runtime.mjs
node experiments/a16/serve.mjs
```

表示されたlocalhost URLを開きます。実行中の本番PCサーバーには接続しません。初回のモデル取得は各1.7〜2.4GB前後です。容量の人工的な上限は設けず、ブラウザが報告する保存量・制限と実際の失敗を記録します。異なるモデルは逐次読み込み、前のWorkerを終了します。結果を保存してから、不要なモデルのキャッシュを削除できます。

`setup-runtime.mjs` は固定バージョンのnpm配布物のSRIを照合し、必要なブラウザ資産をコピーします。npmのインストールスクリプトは実行しません。モデルとWASMの上流リビジョンは `models.json` に固定しています。モデルの重みはGitや配布ZIPに含めません。

## iPad A16での実測

1. 同梱の静的ラボを**本番と異なるoriginのHTTPSホスト**に配置します。`index.html` と同じ場所に各mjs/json/css、`sw.js`、`vendor` が必要です。GitHub Pages本番と同じホストの別パスは避けてください。本番は撤去済みモデルの共有キャッシュを削除するため、ラボ側も本番ホストでのモデル起動を拒否します。開発PCのLANアドレスへの単なるHTTP接続や、iPadの「ファイル」からHTMLを開く方法ではsecure contextになりません。
2. A16実機の「設定」でモデル名・iPadOS版を確認し、Safariの通常タブで開き、端末欄に記録します。OS更新や他のブラウザで試す場合は別測定にします。UA・画面サイズのみではA16の証明になりません。
3. 他の大きなアプリ・タブ数、充電状態、端末の熱さ、Wi-Fi条件、開始時の空き容量をメモします。「端末の対応を確認」でWebGPU、shader-f16、buffer上限、storage estimateを保存します。Neural Engineや物理RAMの総量はWebGPUの返す値ではありません。
4. 「画面を保存」→モデルを1つ選択→「取得して比較」。モデルの初回取得、ウォームアップ、固定10問、4往復の会話、Worker終了後の保存済み再起動を自動記録します。結果JSONを端末外にも保存します。
5. 機内モードをON、Wi-FiもOFFにして、ページを実際に再読み込みします。「保存済みモデルで回答」を実行し、モデルだけでなくページ全体のオフライン再起動を確認します。`navigator.onLine`だけでなく実際のネットワーク切断を記録してください。
6. Safariを背景に移して戻る、画面をロックして解除、タブを閉じて再度開く、別モデルへ切替を試します。自動リロード・中断・失敗の時刻を記録してください。OSによるメモリ不足と単なるタブ終了はページ側から区別できません。真のピークRAM/GPUメモリは接続したMacのSafari Web Inspector / Instruments等で別測定が必要です。JS heapと保存領域をRAM扱いしないでください。
7. 「長い履歴を確認」で21往復分の固定履歴を入力し、冒頭の情報を保持できるか確認します。これは固定した過去の回答を含む検査で、実際に21往復生成した会話ではありません。実際の10分以上の会話と主要問題の3回反復も別に確認します。標準の4往復だけを長時間安定性の証明にしません。冷間・温間・背景復帰の結果を混ぜず、温間初字、生成速度、打ち切り、誤答を個別に判断します。
8. 「選択モデルのキャッシュを削除」後の使用量と、オフライン起動が明確に失敗することを確認します。新モデルへの切替時、学習データ・他モデルのキャッシュが消えないことも確認します。

Safariは保存領域を回収することがあります。`persist()` の成否は保持の保証ではありません。空き容量とRAMは別です。保存し直せば動く状態と、毎回ネット接続を必要とする状態を区別してください。

## 自動測定・記録

```powershell
$env:RISE_PLAYWRIGHT_MODULE='Playwrightのindex.js絶対パス'
node experiments/a16/test-ui.mjs
node experiments/a16/benchmark.mjs Qwen3-4B-q4f16_1-MLC
node experiments/a16/probe.mjs context Qwen3-4B-q4f16_1-MLC
node experiments/a16/probe.mjs delete Qwen3-4B-q4f16_1-MLC
```

実際のChromiumで推論し、固定ポート4327・独立プロファイル `profile/` を使います。`results/` に各質問後のチェックポイント、回答原文、token数、初字時間、runtimeのdecode速度、総時間、エラー、storage estimateを保存します。`outputTokensPerSecond` はprefill込みの総時間から計算した値で、純粋なdecode速度と異なります。WebLLMは各質問でKVをリセットします。会話は全履歴を入力し直す方式です。wllamaのキャッシュ再利用設定は測定条件に明記します。

標準条件は文脈4096、最大256出力、temperature 0.2、top_p 0.9、seed 42。MLCのQwen3系だけ非思考モードを指定します。Qwen3-4B-Instruct-2507は非思考専用モデルで、Unsloth変換のQ3_K_Mを追加比較します。同じseedでもランタイム間で同じ乱数列・回答は保証されません。量子化の違うMLCとGGUFを、ランタイムだけを変えた完全な対照実験とは扱いません。GGUF 2種はいずれも2GiB未満の単一ファイルですが、Safariでの成功は実機測定が必要です。

`RISE_BENCH_PROFILE` で独立プロファイルの保存先を変更できます。`context` / `delete` の補足結果はそれぞれ1ファイルに保存されるため、複数モデルは同じコマンドに続けて指定してください。補足試験を再実行すると同名ファイルを上書きします。配布ZIPには推論コードを同梱し、モデル重み・Chromeプロファイル・利用者の会話は同梱しません。

比較は10問の原文を読み、正誤・日本語・説明の矛盾・未知情報への対応を評価します。キーワード一致で自動採用しません。実機の速度・安定性・オフライン再読み込みが未確認の場合も本番へ統合しません。

## ライセンス

- WebLLM: Apache-2.0。wllama: MIT。配布物のライセンスを `vendor` に同梱します。
- Qwen3 / Qwen3.5: Apache-2.0。Qwen2.5 **3B**は `qwen-research` であり、他サイズと同じApache-2.0だと扱いません。本ラボは比較研究用です。製品への採用にはその用途に合う条件の確認が必要です。
- 各原モデル・量子化変換・runtimeは別の配布物です。固定URLと出典は `models.json` と比較レポートを参照してください。
